# ADR-0011：文件变更审批先落库，批准不直接写盘

- 状态：已实现审批记录阶段，实际应用待 M3 后续阶段
- 日期：2026-09-23

## 背景

`propose_file_change` 已经可以生成完整 diff，但把审批按钮直接连接到文件系统会把网络请求和持久化状态之间的竞态变成真实副作用。Runner 重启、重复点击、工作区文件被其他任务修改，以及审批策略升级都必须有明确的恢复语义。

## 决策

1. 工具成功后，在与 Tool Step 同一事务中创建 `file_change_reviews` 记录。记录绑定 Run、Step、完整预览、预览摘要、策略版本和 24 小时过期时间，并写入 `file_change.proposed` 审计与 Run 事件。
2. 审批接口只允许已登录且拥有该 Session 的用户访问；viewer 不能决定；Workspace、Session、Run 和提案必须同时匹配。批准前重新校验摘要、策略版本、Run 已成功且未取消、有效期和当前状态。
3. 相同状态的重复决定幂等；不同决定、摘要变化、策略变化和已结束状态返回冲突；过期提案第一次被处理时显式变为 `expired`。
4. 审批响应和界面明确返回 `applied: false`。批准只代表人审阅了精确预览，不代表文件已修改。

## 后续应用条件

真正写入必须由 Runner 在非特权沙箱中执行，并且只接受单文件精确内容：重新读取目标文件，前置 SHA-256 与提案一致，策略和审批未过期且未消费，然后以原子替换写入并记录实际结果。校验失败、租约丢失或结果不明时不能自动重试，也不能把批准状态伪装成已应用。

## 验证

- 提案由 `finishToolStep` 持久化，和 Tool Step 状态、事件、审计保持同一事务。
- API 集成测试覆盖完整摘要、错误摘要 409、viewer 403、跨用户/跨 Workspace 404、重复批准幂等、冲突决定和过期提案。
- 没有 PostgreSQL 时集成测试会跳过；CI 使用临时 PostgreSQL 执行该套测试。
