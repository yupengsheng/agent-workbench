# 长期维护约定

## 架构与版本

保持一份决策索引，改动架构时提交新 ADR 并明确替代范围；历史 ADR 保留。公开契约按版本兼容，领域包不暴露供应商对象。架构图、原型和产品说明明确“目标”与“实现”，阶段门槛按证据更新。

Node 默认 24 LTS，22 临时兼容；M1 完成前迁出 22 生产基线。每季度检查上游支持期限，至少在 EOL 前 6 个月安排升级。依赖通过锁文件重现，每月评估更新，每季度做数据库/运行时升级演练；安全修复按影响分级，不自动合并主版本升级。

## 组件治理

设计 tokens 为浏览器原型和 Figma 的共同输入，组件有状态/键盘/空态定义。生产应用按 feature 切分；相同职责在两处以上复用时再抽公共组件，不把领域行为塞进通用 Button/Table。

为新增状态和动作同步更新协议、Figma 交互、UI reducer 与负向测试。设计组件名与代码组件映射保存在 module-boundaries.md，视觉变化不应修改引擎。

## 可靠性与测试

使用注入端口代替在测试里连接真实供应商；将模型质量评测与程序正确性分开。正常、拒绝、超时、取消、重启、重复、乱序和结果不明都纳入验收。

PR 必须说明问题、行为变化、验证证据、迁移与恢复影响。CI 保护合并；初期单人项目由可执行检查和变更说明建立记录，团队增长后给身份/运行/安全领域设置真实负责人，而不虚构负责人。

## 数据演进

生产迁移采用 expand → migrate → contract，旧新应用兼容窗口明确。大表回填单独作业并限速；删除字段前确认读写路径已迁移。日志/审计/事件/产物分别定义保留和脱敏，备份包含恢复演练而不只“备份成功”。

## 依赖与供应链

每个运行依赖登记来源、许可证、维护状态、必要性和替换路径。项目 Apache 许可不能覆盖外部依赖；分发时保留适用第三方通知、生成 SBOM 并检查镜像依赖。原型使用文本与几何形状，无需引入外部图库或字体资产。

贡献使用 DCO `git commit -s` 确认提交权利，默认贡献按 Apache-2.0；不自动要求版权转让。新贡献需保留来源，不能将未知来源代码标为原创。

## 决策复评触发

运行异常率超过约定基线、无法满足取消/恢复语义、三种以上供应商适配持续重复、CI P95 > 5 分钟、必须支持多节点高可用或不可信多租户时，复评框架/队列/部署与沙箱。每次复评列迁移成本、兼容方案、数据迁移和退出计划，避免仅因流行趋势迁移。
